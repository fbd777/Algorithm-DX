# DX Rating 与 B50 计分说明

未计时题目不视为必须完成的任务：默认只提示最近 7 天实际 AC、尚未计时且未忽略的题目。更早的题目归入「历史未计时」，不会因今天刚同步就冒成新任务。「不再提醒」只保存偏好，不删提交或成绩，可恢复或直接补录。无可信用时的题目不估算分数。总览展示已记录成绩数量；补录清单每页 20 题。偏好按账号隔离（schema v12）。

新增「专注计时」：准备好题目和 IDE 后，输入 Codeforces 题号或链接并开始，无需预先有提交。计时会持久保存在 `practice_timers`（schema v11），本机面板服务每约 30 秒同步正在计时的账号；只有同账号、同题目、开始后的 AC 才会结算，取最早匹配提交的时间，爬取延迟不计入。同步事务内追加练习记录并更新最佳用时，同一计时不会重复保存；取消不生成成绩。辅助解题不计分。刷新、跨页、关闭浏览器后可恢复；服务关闭时暂停抓取，重启后检查历史 AC。计时上限 24 小时，超时在下一轮同步核对后结束。计时来源在历史与回测来源统计中单列，现有手动计时校准样本口径不变。

「全部成绩」提供全部已保存的每题最佳有效成绩（不限 B50），支持难度、完成度、用时范围与评级、分区、上榜状态、关键词联合筛选；支持 11 种排序、网格/列表、分页、评级快捷筛选、CSV 导出及「再练一次」。统计卡展示全库，结果数与导出跟随筛选；未评级成绩保留，缺失数值不会当作 0 参与范围筛选。

更新到此版本后，先运行 `npm run db:init` 迁移数据库，再重启面板服务。计时数据与成绩都保存在本机，不上传到外部服务。

页面按「Rating 总览 → 补录与历史 → 全部成绩」组织。总览展示总分、分区占位和已记录成绩，仅在近期有可补录题目时提供可选提醒；空位汇总为一行提示。「补录与历史」内可切换可补录题目与历史记录，历史排序仅在历史视图显示。「全部成绩」支持题号、题名与上榜状态联合筛选。新旧题依据出题年份划分，年度选择不筛选练习日期；评分公式与最佳成绩选取仍由服务端统一计算。

面板顶栏的「DX Rating」（`/dx.html`）是一个娱乐向的换算页：把你在 Codeforces 上 AC 的题按**完成用时**折算成 maimai DX 形式的单题 rating，排成上 7×5 旧题、下 3×5 本年度新题的 50 格榜。

三条口径全部在服务端定死，前端不做任何计算：

- **只算 Codeforces。** CF 的题目 Rating 是官方数字，可以直接充当难度锚点（对应 maimai 的「定数」那一层）；其他平台没有同口径的锚点（洛谷只有等级码 0–4，要凑出来得先做一套人为映射，那是另一个决定）。
- **只有填过用时的题进榜。** 没填的**不计 0 分，是不存在**。在「待填写用时」列表里挑一道题填上（时/分/秒三格分开填，留空的按 0 算）即可，也可以从榜上的卡片点「改用时」。
- **未评定的题现在就能填。** CF 比赛刚打完时还没公布题目 Rating，这样的题带着「未评定」标记出现在待填写清单里 —— 用时照填，**不进榜但等评级**：同步会用 `problemset.problems` 把库里为 NULL 的 `difficulty` 自动回填（见下一节），一回填、下一次读取就计分进榜，不需要任何人再动它。gym / unrated 场的题永远等不到官方评级，就永远不进榜 —— 那是事实，不是缺数据。
- **新题 = 本年度出的题。** 看的是题目的**出题日期**（它所属比赛的开始时间），边界是本地时区 1 月 1 日 0 点（左闭），最多 15 道；更早的最多 35 道。**与 AC 时间无关** —— 2026 年补做一道 2013 年的题（比如 `339:A`），它仍然进旧题区，不会冒充新题。查不到出题日期的题（例如 gym 题）按旧题处理，页面上会把数量报出来。

出题日期不在提交载荷里：CF 的 `user.status` 只给 contestId 与 Rating。它来自 `contest.list` 的比赛开始时间，同步时按 6 小时 TTL 落到 `contests` 表（schema v6），再由 `problem_id` 的前缀（`339:A` → 339）联出来。取不到**不算同步失败**（提交已经到手了），但会写进同步记录，不静默吞掉。

题目 Rating 也有同一条链路，只是多一环：提交载荷里的 `difficulty` **只在抓到那条提交的当时**有值 —— 比赛刚打完时 CF 还没公布评级，那次抓回来的就是 NULL，而近期同步只刷最近窗口，题一旦滑出窗口就永远补不上。所以同步在**事务提交之后**会用 `problemset.problems`（全量题目评级，缓存 6 小时）把为 NULL 的 `difficulty` 回填；`submissions` 的 upsert 对这一列用 `COALESCE`，保证「还没公布」的 NULL 不会把已回填的官方评级盖回去。回填了多少条、失败原因，都拼在同步回执里。

```
完成度 A：用时 ≤ T97 → 六个锚定节点之间**线性插值**（连续，不是「过线就取门槛值」）
            SSS+ 0.646 ↔ 100.5%    SSS  0.732 ↔ 100%     SS+ 0.797 ↔ 99.5%
            SS   0.846 ↔ 99%       S+   0.939 ↔ 98%      S   1.000 ↔ 97%   （用时 ÷ T97）
          更快 → A = 101 − 0.5 × (用时 ÷ T97) / 0.646；用时趋近 0 时趋近 101%
          用时 > T97 → ln(用时/T97) = a*d + b*d²，A = max(0, 97 - d)
          a = ln(1/0.732)/3，b = 0.01，d 取非负根
          （评分仍按 100.5 封顶；正用时的完成度在数学上小于 101）
系数因子 F(A) = A × 评级系数(A) / (97 × 20.0)              A ≤ 97（maimai 原样）
              = 1 + (上式 − 1) × 1.6                      97 < A ≤ 100.5（放大 K）
单题 rating = (题目 Rating / 50) × F(A)
总 Rating  = 各格单题 rating 之和
```

`T97` 是「该难度的题，完成度 97% 所需的用时」，来自 Codeforces × maimai 统计实验拟合出来的曲线（详见 [docs/cf-maimai-study.md](cf-maimai-study.md)）。`评级系数(A)` 照搬 maimai 的达成率系数阶梯表（SSS+ 22.4、SSS 21.6、S 20.0、AAA 16.8、A 13.6、C 8.0 …），除以 `97 × 20.0` 是为了把 **97% 归一到 1.000**。

于是：用时正好等于 T97 时单题 rating 恰好是 `题目 Rating ÷ 50`（1400 的题就是 28.0 分，Rank S）；**97% 不是满分 —— 满分要压到 0.646 × T97 以内（100.5% / SSS+），拿的是 1.257 倍**，1400 的题得 35.2。

**K = 1.6 这一层放大是本项目加的，maimai 没有。** 它的语义是：97% = 刚好这题的水平（50% 把握），100% = **几乎稳定切**。实测「稳定切」是 90% 解出率、对应 Rating 差 **+217 分**，且不随题目难度变（`SOLVE_RATE_PROBE.md`）；折算到加权平均难度 1197 上就是 100% 处的 F = 1.181，反推出 K = 1.6。**它只放大幅度、不动形状** —— 97→100 与 100→100.5 两段增量的比例照 maimai 一字未改，97% 及以下也一个字没动。

S 及以上六档的用时门槛按**等效选手 Rating** 锚定：取 `q × 系数因子` 那一档选手在该题上的中位用时当门槛，S 档（系数因子 1.000）正好就是 T97。改 `TOP_FACTOR_GAIN` 后需要重跑 `anchor-by-player-rating.mjs` 并更新六个时间比。评级系数仍是阶梯，97% 处存在评分跳变。

**2026-10-03：97% 以下改为逐渐放缓的设计曲线。** 每下降 3 个百分点的时间倍率依次增大：100→97 为 1.366、97→94 为 1.495、94→91 为 1.790、91→88 为 2.143。2 倍 T97 得 92.38%，4 倍得 89.33%，1400 题用 75 分钟约得 92.57%。参数 b=0.01 是评分设计，不是数据拟合结论。远端非常宽松：80% 约需 105.41 倍 T97，低于 50% 的零分门槛约为 5.203×10¹¹ 倍 T97，不能用该门槛约束实际输入。历史耗时不重写，评分在读取时重新计算，B50 选题可能变化；回测分别保留旧算法与新版 `gentle-decay-v3`。

**完成度是「用时 ÷ T97」的连续函数，理论极限为 101%**。档间按线性插值算（0.98 × T97 拿到的是 **97.33%**，不是 97 或 98），显示到小数点后 4 位。2026-09-22 起，比 SSS+ 门槛还快改走独立尾段 `A = 101 − 0.5 × (用时 ÷ T97) / 0.646`，正用时在数学上始终小于 101%，不再把所有 ≤0.56×T97 的成绩显示成 101%。例如 0.323×T97 对应 100.7500%，0.1292×T97 对应 100.9000%。**评分仍按 100.5 封顶**，本次不改变单题 Rating、Rank 和 B50 排序；尾段是产品设计候选，尚未以训练充分人群的 B50 分布校准。总分按**各格已取整到 1 位小数的值**相加，所以界面上的数字加起来就等于总分。

**当前正式 T97（2026-10-06）采用指数趋缓加线性增长模型，覆盖 800–3500。** 参数保存在 `results/cf-study/t97-production.json`，`npm run study:export-dx` 导出 `src/dx/curve.ts`；实际评分直接求公式值。2500 / 3000 / 3500 的 T97 分别为 48.06 / 52.09 / 56.12 分钟，完整值见 [正式 T97 表](../results/cf-study/T97_PRODUCTION_TABLE.md)。拟合使用 800–2000 的七个旧曲线代表值，2000 以上为用户确认采用的外推，尚无独立比赛验证，故统计验证标记 `productionReady=false`，不影响启用。帮助页区分启用范围与拟合输入范围。原 800–2400 经验曲线和验证报告保留作研究对照，不能把旧曲线的验证结论用于新模型；需要切回时显式运行 `npm run study:export-dx -- --empirical`。超过 3500 继续按端点夹取并标记。修改参数、重新导出并重启面板即可更新评分，不改原始耗时记录。

换算与取榜规则只有一处实现（`src/dx/rating.ts`），写操作只有一处实现（`src/dx-admin.ts`），前端只负责显示与回写。
