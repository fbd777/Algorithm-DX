# Codeforces × maimai DX：统计实验与修订方案

本阶段只实现数据抓取、清洗、生存统计和可导出的 PNG/SVG 图，不做前端。抓取与统计使用 Node.js 24，无新增 Node 运行依赖；科学绘图使用可选的 Python + matplotlib，不影响原有练习记录数据库。

## 补充方案的语义调整

最新要求采用**成功者的中位完成度约为 97%**。选择中位数而不是平均值，因为中位数在严格单调的耗时→完成度变换下仍能对应；平均值没有这个性质。

必须区分两个时间：

- `T_solve50`：包含未解出者的加权 Kaplan–Meier CDF 首次达到 0.5 的时间。保留旧名字 `t97KmSeconds` 方便与原方案比较，但不再把它直接用于新方案的 97% 锚点。
- `T_success50`：比赛内成功者的加权耗时中位数，输出 `successP50Seconds`。这是补充方案的候选 97% 锚点。它受比赛时长和成功者选择影响，不代表所有最终能够解出的人。

“同 Rating 有 50% 概率解出”是需要实测检验的假设，不能通过定义 97% 使之成立。如果同一固定观察窗口内最终解出率恰好 50%，成功者中位时间对应总体累计解出概率约 25%，不是 50%。不同剩余比赛时长下更不能直接用固定的二倍换算。

为兼容补充要求的“97% 单题 rating 等于题目 rating”和原有 B50 量纲，采用 maimai DX 单谱面 rating 的实际形式：

```
maimai：单谱面 Rating = 定数 × (达成率 / 100) × 评级系数(达成率)
此处：  单题 rating    = (题目 Rating / 50) × A × 评级系数(A) / (97 × 20.0)
总 Rating = 旧题 Best35 的贡献之和 + 当年新题 Best15 的贡献之和
```

关键在那层**评级系数**，它是按档位查表的常数（SSS+ 22.4、SSS 21.6、S 20.0、AAA 16.8 …），不是常数倍；除数 `97 × 20.0` 把「97% 处」归一到系数 1。因此 1400 题、97% 时单题贡献是 28。**97% 是锚点，不是满分** —— 满分在 100.5%（SSS+）：maimai 原样是 100.5 × 22.4 / (97 × 20) = 1.160 倍，再过一层放大 K = 1.6 得 **1.257 倍**，即 35.2。50 题全是 S 表现时总分 1400，不再除以 50。不增加 AC 奖励，不添加 WA 惩罚；WA 暂作辅助数据。缺题不补满，重复同题只留最佳成绩。

> **年份口径：按题目发布时间划分（2026-09-18 定稿，同日曾短暂改成 AC 时间，当日回退）**
>
> 最终规则是**题目的出题日期落在哪个自然年**：本年度**新办比赛**里的题进新题 b15，更早的进旧题 b35。边界是本地时区 1 月 1 日 0 点、左闭。
>
> 中途（同一天早些时候）客户端一版实现按「该题**最早一次 AC 的时间**」划分，理由是「玩家关心的是我今年做了哪些题」。实测后废弃：CF 上绝大多数练习都是**补做往年老题**，按 AC 时间划分会让 2013 年的题（如 `339:A`，Codeforces Round 197）顶着「新题」标签挤满 b15，b35 反而空着 —— 而 maimai 的 b15 本来就是「今年新出的谱面」这一层含义。出题日期不在提交载荷里，由 `contests` 表提供（`contest.list` 的 `startTimeSeconds`，见 `src/db/migrations/006-contest.sql`）。查不到出题日期（例如 gym 题）时**按旧题处理**，并在页面上把数量报出来。
>
> 仍未处理：跨 Div 共享题目的去重（CF 的 `problem_id` 形如 `2259:C`，跨 Div 共享题目会各自计一次）。

Rank 已补齐：D <50；C ≥50；B ≥60；BB ≥70；BBB ≥75；A ≥80；AA ≥90；AAA ≥94；S ≥97；S+ ≥98；SS ≥99；SS+ ≥99.5；SSS ≥100；SSS+ ≥100.5。完成度显示上限仍为 101，Rating 计算上限为 100.5。参考 [maimai 社区计算器作者的档位验证](https://sgimera.github.io/mai_RatingAnalyzer/maidx_rating.html)，不是 SEGA 官方公布的算法承诺。评级系数 K(A) 也已经落地（客户端一节的阶梯表，归一到 97% = 1）；maimai 表里那几个**宽度 0.0001 的档位极大值系数**（100.4999 → 22.2、99.9999 → 21.4、96.9999 → 17.6、79.9999 → 12.8）按不可达处理，未收录 —— 本地输入是用时（整秒），这类窗口只有几毫秒宽。

## 映射到客户端（DX Rating 页）

2026-09-18 起，这套换算是面板里的**独立一页**：`npm run dashboard` → 顶栏「DX Rating」（`/dx.html`）。
形态参照 maimai 的 b50：上 7×5 = 35 格旧题、下 3×5 = 15 格本年度新题，每格显示题目 Rating、题名、单题 rating、完成度与 Rank。

### 客户端口径（三条，全部在服务端定死）

| 规则 | 说明 |
|---|---|
| **只做 Codeforces** | CF 的题目 Rating 是官方给的数字，可以直接当「定数」。洛谷只有等级码（0–4），要凑出定数得先做一套人为映射，那是另一个决定 |
| **只有填过用时的题进榜** | 没填的**不计 0 分，是不存在**。用时由用户在已 AC 的题上手动填（`POST /api/dx/time`），写入前核对这题确实 AC 过 |
| **新题 = 本年度出的题** | 看**出题日期**（所属比赛的开始时间），边界是本地时区 1 月 1 日 0 点，左闭。最多取 15 道；更早的最多取 35 道。**与 AC 时间无关** —— 2026 年补做 2013 年的题仍进旧题区 |

### 用时 → 单题 rating

客户端没有 maimai 的达成率，只有「这道题做了多久」，所以换算入口是**用时与 T97 的比值** `r = 用时 ÷ T97`：

```
完成度 A：0 < r < 0.646 时 A = 101 − 0.5 × r / 0.646
          0.646 ≤ r ≤ 1 时走 TOP_TIME_RATIOS 的分段线性
          r > 1 时 d = 2 ln(r) / (a + sqrt(a² + 4b ln(r)))，A = max(0, 97 - d)
          a = ln(1/0.732)/3 ≈ 0.10399158834，b = 0.01
系数因子 F(A) = A × 评级系数(A) / (97 × 20.0)
单题 rating = (题目 Rating / 50) × F(A)
总 Rating  = 各格单题 rating 之和（旧题 35 + 新题 15）
```

**S 及以上六档的用时门槛不是从 maimai 的分数档位折算来的。** 折算的结果是
0.965 / 0.970 / 0.975 / 0.980 / 0.990 / 1.000：六档一共只用掉 3.5% 的时间余量，在 800 档上
相邻两档只差 **6 秒**，标签等于没有信息量。根因是把 maimai 的**分数**档位（高手挤在 1% 以内，
0.5% 一档才有意义）原样搬到了「用时的倒数」上，而用时是散开的（800 档 P10/P50/P90 = 397 / 1216 / 3619 秒）。
2026-09-18 起改按**等效选手 Rating** 锚定：

```
t_rank(q) = 中位用时( 题目 Rating = q ｜ 选手赛前 Rating ≈ q × 系数因子 )
```

本项目里 `总 Rating = 各格单题 rating 之和（50 格）`，于是「单题 rating × 50」就是等效 CF
Rating；S 档（系数因子 1.000）的参照选手正好是 rating ≈ q 的人 —— **这正是 T97 原本的定义**。
这条规则没有另起炉灶，只是把同一个锚点沿系数因子往上推，六档因此落到 **0.646 ~ 1.000** 上，
一档差 40 秒（800 档）到 2.5 分钟（2000 档以上）。

⚠️ **这六个数随 `TOP_FACTOR_GAIN`（K）一起变，改 K 必须重跑重填。** 2026-09-18 把 K 从 1.0
抬到 1.6 之后，SSS+ 的参照选手从 1.160q 变成 1.257q —— 更强，所以中位用时更短，门槛由
0.755 收紧到 0.646。看起来是「变难了」，其实是自洽的：SSS+ 现在宣称的是更高的等效 Rating，
理所当然要用更快的用时才够得着。S 档（系数因子恒为 1.000）不受影响，仍然就是 T97。

数据、逐档表与灵敏度：`results/cf-study/PLAYER_ANCHOR.md`（离线重跑 69 场，选手 Rating 窗口 ±500，
1,742,368 行样本；四个灵敏度配置 ±75/±100/±150 半径 × σ 50/75/100 下，六个比值都稳在 ±0.015 内）。
**只覆盖 S 及以上** —— 再往下（AAA/AA）的参照选手跌到题目 Rating 的 81% / 71%，超出采集窗口
且样本只剩几十条，比值已经不稳（1200 档 AAA 与 AA 甚至反序）。S 以下自 2026-10-03 改用独立设计曲线 `ln(r) = a*d + b*d²`，其中 `d = 97 - A`。参数 a 参考现有 100→97 的时间倍率，b=0.01 是用户确认的评分设计，非实测分位点。每下降 3 个百分点的时间倍率从 100→97 的 1.366，依次变为 97→94 的 1.495、94→91 的 1.790、91→88 的 2.143，严格增加。2 倍 T97 对应 92.38%，4 倍对应 89.33%；当前 1400 档耗时 75 分钟约为 92.57%。曲线在 97% 处连续，但不要求两侧导数相同。完成度最低为 0；反算接口只接受大于 0 的完成度，避免最低值对应一段时间而没有唯一逆。

`评级系数(A)` 照搬 maimai 的达成率系数表 —— **档内是常数，不插值**，所以整条是阶梯：

|---|---|---|---|---|---|
| 100.5%（评分上限） | SSS+ | 22.4 | **1.257** | ≤0.646 | **35.2** |
| 100.0% | SSS | 21.6 | 1.181 | ≤0.732 | 33.1 |
| 99.5% | SS+ | 21.1 | 1.132 | ≤0.797 | 31.7 |
| 99.0% | SS | 20.8 | 1.098 | ≤0.846 | 30.8 |

**97% 以上那一截另有一层放大 K = 1.6（`TOP_FACTOR_GAIN`），maimai 没有。**

```
F(A) = A × 评级系数(A) ÷ (97 × 20)          A ≤ 97      ← maimai 原样，一个字不改
F(A) = 1 + (上式 − 1) × K                   97 < A ≤ 100.5
```

语义是 Ryan 定的：**97% = 刚好这题的水平（50% 把握），100% = 几乎稳定切**。实测「稳定切」=
90% 解出率、对应 Rating 差 **+217 分**，而且这个差**不随题目难度变**（`SOLVE_RATE_PROBE.md`）；
他不要按难度做差异化系数，于是折算到加权平均难度 1197 上取一个确定的系数
(1197 + 217) ÷ 1197 = **1.181**，反推出 K = (1.181 − 1) ÷ (1.113 − 1) ≈ **1.6**。

**K 只放大幅度，不动形状**：97→100 与 100→100.5 两段增量的比例照 maimai 一字未改（把上表
`F(A)` 那一列各减去 1，相邻档之间的比值与 K = 1 时完全相同），97% 及以下也一个字没动。
这一点由测试钉着 —— 改 K 时 `tests/dx-rating.test.ts` 里那两条断言会先炸。

**已知的代价（乘性形状自带，不是 bug）**：K 乘的是题目 Rating，于是同一个完成度在不同难度上
换到的**绝对分差**不同 —— 1200 的题 @100% 等效 +220、2000 的题等效 +365，而实测说两处都该是
+217。要让它们一样，得把形状换成**加性** `(题目 Rating + Δ(A)) ÷ 50`（Δ(100%) = 217）。
那是另一处改动，`MAIMAI_SCALE.md` 表 7 有完整对照，等 Ryan 定。

五点必须说清的：

- **完成度是「用时 ÷ T97」的连续函数，不是一张离散的档位表。** 上表每一行的完成度是那一档的**门槛**（进档值），档间按**线性插值**算：S（1.000 × T97 ↔ 97%）与 S+（0.939 × T97 ↔ 98%）之间的 0.98 × T97 拿到 **97.33%**，而不是 97 或 98 —— 所以它**显示到小数点后 4 位**（`ACHIEVEMENT_DISPLAY_DECIMALS`，与 maimai 的达成率同一精度），截成整数会把「快一点」和「快很多」又抹平。2026-09-22 起，比 SSS+ 门槛还快改用独立尾段 **`A = 101 − 0.5 × r / 0.646`**，与 100.5% 连续衔接，用时趋近 0 时才趋近 **101%**。例如 r=0.56 对应 100.5666%，r=0.323 对应 100.7500%，r=0.1292 对应 100.9000%。该尾段是产品设计候选，尚未经过训练充分人群的 B50 回测；原有六档时间门槛、T97 和评分系数保持不变。反算时 101% 返回理论边界 0 秒，超过 101% 报错；实际用时仍要求正数。
- **97% 是锚点，不是满分。** 用时正好等于 T97 时 A = 97、F = 1.000、单题 rating = 题目 Rating ÷ 50（1400 的题就是 28.0），与上文的 97% 锚点一致。**满分在 100.5%（SSS+），是 1.257 倍** —— 比锚点高 25.7%，其中有三层：达成率本身、评级系数从 20.0 涨到 22.4 的那一段、以及 `TOP_FACTOR_GAIN` 这层放大。写成 `clamp(A,50,100.5)/97` 是错的：那让 SSS+ 只比 S 高 3.6%，等于把「上限」当成了「满分」。
- **97.00% 处有一道 19% 的台阶。** 系数表是阶梯，96.99%（AAA）的 F 只有 0.840，一过线就是 1.000 —— 从下往上看是 **+19%**，从上往下看是 −16%。这是 maimai 的原样 —— 够到 S 本身就值钱。代价是「用时 1.0001 × T97」比「1.0000 × T97」低 16%，这是形状决定的，不是 bug。档内 F 随 A 线性上升；A = 98 / 99 / 99.5 / 100 处另有**四道**小台阶（K = 1.6 下各约 +3% ~ +6.5%）。用时那侧它们不再挤在一起：六个锚定节点把每道门槛钉在 **0.939 / 0.846 / 0.797 / 0.732 / 0.646 × T97** 上，所以每道台阶都有明确的时间坐标，而不是笼统的「99.0% 与 100.0%」。
- **A < 50 不计分是本项目的取舍**，不是 maimai 的规则。慢速段改为缓衰减后，这个门槛约为 5.203×10¹¹ 倍 T97，实际练习基本不会触及，不能再用它约束乱填用时；80% 也要约 105.41 倍 T97 才会达到，这是该设计在远端很宽松的代价。**评分时完成度按 100.5 封顶**（`ACHIEVEMENT_RATING_MAX`），最高贡献为锚点的约 1.257 倍。**101% 是理论极限**，正用时在数学上达不到它。2026-10-03 的慢速段调整会提高原先低于 97% 的成绩，可能改变单题 Rating 与 B50 选题；97% 及以上的时间节点、评级系数与 T97 拟合表不变。
- **系数表出处**：萌娘百科 maimai DX 词条与 gekichumai 的 DXRating 计算器（第 28 行引的就是后者），两处数值一致。maimai 表里另有几个宽度 0.0001 的档位极大值系数（100.4999 → 22.2 等），按不可达处理，未收录。

**唯一出处**：`src/dx/rating.ts`。面板**不做任何口径计算** —— 单题 rating、完成度、Rank、b35/b15 的选取全在服务端算好，前端只负责显示与回写。与统计线里 `problem-scope.ts` / `core.mjs` 是同一条规矩。总分的定义是**各格已取整到 1 位小数的单题 rating 之和**，这样界面上的数字相加就等于总分，不会出现「怎么算都对不上」。

### 曲线是导出的，不是抄的

`npm run study:export-dx` 把 `results/cf-study/t97_monotone.csv` 的 `success`（成功者中位耗时）单调列导出成 `src/dx/curve.ts`，并嵌入源文件 SHA256、`diagnostics.json` 的 `productionReady` 与判据说明。导出时会断言：端点等于 `FIT_MIN_Q`/`FIT_MAX_Q`、步长 25、严格不下降、全为正 —— 任一条不满足就直接报错，不生成坏曲线。

所以**改曲线只有一条路**：跑完统计链 → `npm run study:export-dx`。手改 `src/dx/curve.ts` 会在下次导出时被覆盖，而面板上没有第二份数字。

`GET /api/dx` 会把 `productionReady`、源文件、生成时间、源指纹一并返回，页面顶部据此显示状态条：判据没过就是**黄底警示**（「这是探索性估计，别当实测点读」），全过就是**中性色**（「已通过三条判据」）—— 两种状态都留在页面上，因为曲线一改面板上所有读数都跟着变，指纹必须看得见。**当前是 `true`**（2026-09-18，题位冷启动口径修好之后第三条判据才通过）。

### 数据

新表 `problem_times`（schema v5）：`(user_id, platform, problem_id)` 唯一，存用户填写的**原始秒数**。
不存换算后的 rating（曲线一改所有读数都得变，落库就多一个真相来源）。AC 时间与**出题日期**都不在这里重复：待填写清单按 `submissions` 里该题最早的 AC 时间倒序，而进 b35 还是 b15 由 `contests` 里的比赛开始时间决定（`problem_id` 的前缀就是比赛 id）。

新表 `contests`（schema v6）：`(platform, contest_id)` 主键，存 `name` 与 `start_time`（= 出题日期）。
来源是 CF 的 `contest.list?gym=false`（一次 2154 场 / 409 KB，没有分页参数），由同步流程按 **6 小时 TTL** 拉取、upsert 写入 —— 比赛开始时间是既成事实，只有新办比赛才会新增。
**不按 `type` 过滤**：`contest.list` 的 `type='ICPC'` 不是「ICPC 赛制」，Div.3 与 Educational 全是它，按 `type==='CF'` 筛会漏掉低分选手最早拿 rated 记录的那批比赛。取比赛列表失败**不算同步失败**（提交已经到手了），但会把「出题日期未更新（…）」写进 `sync_runs.message`，不静默吞掉。

写入口径在 `src/dx-admin.ts`：必须先是该用户在该平台 AC 过的题；秒数取 1 秒 – 24 小时的整数；平台强制为 `codeforces`，不接受请求体指定。

## 运行

### 第二轮扩样：先铺满历史账本，再补薄档位

```powershell
# 1) 铺满历史证据账本（每场 1 个 ratingChanges 请求，约 0.46 MB）
#    注意 --from/--to 是左闭右开：要覆盖到 2026 年，--to 必须写 2027。
npm run study:ledger -- --from=2022 --to=2027 --contests=500

# 2) 用新账本重建已有比赛的全部记录（离线，不发请求）
```

**为什么账本要单独一步**：`priorRated ≥ 10` 这条门槛完全依赖账本证明。原账本只有 97 场、平均每月 1–4 场，于是低档位只有极活跃的老手能过关 —— 800 档窗口内 68025 条记录只通过 2281 条（3.4%），其中 65% 卡在 1–4 场。这既是样本瓶颈，也是选择偏差来源，而且**不会因为多抓比赛而缓解**。`ratingChanges` 每场只有 1 个请求、约 0.46 MB，比抓比赛（每场 3 个请求，其中 `contest.status` 压缩后平均 31 MB）便宜一个量级，所以先铺账本、再谈加比赛。

**账本存在 SQLite 里**（`data/cf-study/processed/history-ledger.sqlite`，表 `rating_changes`，主键 `(handle, contest_id)`）。这不是风格选择：JSON 版本长到 505 MB 时撞上了 V8 的单字符串上限（约 512 MiB），`JSON.stringify` 抛 `RangeError`，而且**从撞上限那一刻起每一次落盘都失败** —— 已经抓到的 19 场只存在于内存里，随进程一起没了。改用 `node:sqlite`（项目本来就用它，仍然零依赖）之后：写入是增量的、没有体积天花板、按 handle 取历史走主键范围扫描、崩了也不会毁掉已写入的部分。旧 JSON 首次运行时自动导入，随后压缩存档到 `data/cf-study/runs/pre-backfill/history-ledger.json.gz` 并删除原文件。

`historyFor()` 的结果按 handle 进程内缓存，**写入时必须失效**：`attachHistory` 要求当前这场比赛也出现在历史数组里（用它核对 `oldRating`），缓存若停留在「那场还没写进去」的时刻，整行会被判 `null` 静默丢掉。缓存由存储层在 `appendContest` / `markContest` 内自动清空，不要在脚本里自己再包一层缓存。

**`contest.list` 的 `type` 字段是个坑**：`'ICPC'` 不代表「ICPC 赛制的比赛」，而是指标准 ACM 赛制 —— `Codeforces Round 1114 (Div. 3)`、`Educational Codeforces Round 194 (Rated for Div. 2)` 全都是 `type='ICPC'`。只有 `'IOI'` 是可以安全排除的（IOI 赛制没有题目 Rating，`candidates()` 本来就返回空）。2022–2026 的 587 场已结束非 IOI 比赛里 `type='CF'` 只有 364 场，按 `type==='CF'` 筛会漏掉 223 场 —— 而 Educational / Div.3 正是低分选手最早拿到 rated 记录的地方，漏掉它们会让低档位的 `priorRated` 系统性偏低，正是要修的那个偏差。判据因此是 `type!=='IOI'` 加一份娱乐场次名单，名单盖不到的由「有没有 Rating 变更」兜底：CF 对 ICPC 区域赛、mirror 之类的场次直接返回 400 `Rating changes are unavailable`，这类场次登记为「已覆盖 0 行」并被 `backfill.mjs` 写进 `manifest.unavailableRatingChanges` 永久排除。

那份名单是 `core.mjs` 的 `UNRATED_CONTEST_NAME`，**`ledger.mjs` 与 `backfill.mjs` 共用同一份** —— 分头维护会让两边互相漏：补比赛曾反复挑中账本早已排除的 mirror 场次（因为它们题目档位多、贪心打分高），白花请求。同理，`backfill.mjs` 还会把账本里 `rows = 0` 的场次一并排除，因为拿不到 `oldRating` 就产不出任何样本。

**为什么目标档位上限是 2100 而不是 2200**：实测 2024–2026 的候选池里，「含该档题目 + 该档至少 25 位参赛者」的比赛数逐档下降 —— 2000 档 42 场，**2200 档只剩 10 场**（放宽到 2022 年才 19 场）。10 场撑不起一个档位（`small_sample` 的门槛是独立比赛 <10），而 2100 档能稳定凑到 15 场。与其把 2200 画成一条权重极低、随时可能反转的线，不如把曲线右端诚实地停在 2100。2200 仍然可以补，只是不列入达标目标。

`backfill.mjs` 与 `targeted.mjs` 的区别：档位不写死，每轮重算「这场能补几个还没达标的档」；年份与比赛族都不设限，Div.1 / Div.1+Div.2 一并纳入（2000 以上的题基本只在那些场次出现，而原先的选择池排除纯 Div.1，正是高段样本断掉的直接原因）；判据是**独立比赛数**而不是样本条数，因为曲线抖动的根源是独立比赛太少，同一场比赛来一千个人也只算一场。两个脚本都支持中断续传：已抓的响应进 `data/cf-study/raw/` 缓存，重跑会跳过。

**贪心打分还会被「有该档题目但没有该档选手」骗**：Div.3 里确实可能出现 2000 分的题，但 Div.3 只对 <1600 的选手 rated，2000 分选手参赛根本不产生 Rating 变更，`candidates()` 一条都产不出来 —— 修前反复挑中 `Codeforces Round 974 (Div. 3)` 去补 2000 档，白花请求。所以判据里加了 `--min-in-window`：这场比赛**真有**该档位的参赛者才算数。证据直接来自账本里每场 `old_rating` 的全量（按 100 分桶建 histogram），不用额外请求。

### 曲线形状：单调约束与未约束对照

`monotone-fit.mjs` 在核平滑之上做一层**加权保序回归**（PAVA），把「同 Rating 下 T97 不应随题目 Rating 下降」写成形状先验，压住右端的局部反转。权重取每处核函数权重之和，所以样本稀少的档位权重低、会被邻近档位拉动 —— 这正是用来压住反转的机制。

代价是它可能掩盖真实反转，因此**未约束版本同时保留**：`t97_smooth.csv` 未约束，`t97_monotone.csv` 约束后，`MONOTONE.md` 逐档给出调整量与该档 95% 区间，`T97_TABLE.md` 把两列并排列出。若某档的调整量落在自身区间之外，说明单调化改写的不只是噪声，该档需要单独审视。

**「未约束对照」不足以保证没吃掉真信号 —— 这是最容易被误读的一点。** 核平滑（带宽由 LOOCV 选出，当前 125）本身就会把相邻档之间几分钟的交替当噪声平均掉，所以真正的反转可能在保序回归之前就已经消失。为了不让这一步被静默跳过，`compare.mjs` 会自动检测**口径稳健的局部反转**并把它们逐条列进 `COMPARISON.md`：判据是「高档位在九种筛选口径（±50/±100/±150 × ≥5/≥10/≥20）下的最大值 < 低档位的最小值」，即换任何一种口径都翻不回来。对每一处还会标出它是在哪一步被抹掉的 —— 核平滑还是保序回归 —— 因为两者代价不同：前者可能连真信号一起吃掉，后者是形状先验与数据正面冲突。当前数据显示 800–2400 之间有 **4 处**这样的反转（1200→1300、1400→1500、1800→1900、2300→2400，两种 T97 定义都成立），所以主推曲线只应读成「在『不随难度下降』这一先验下最保守的估计」，不能当实测点用。前三处是被核平滑抹掉的，**只有 2300→2400 是被保序回归硬压平的**（九种口径下 2300 档 47.15–49.98 分钟、2400 档 42.10–43.65 分钟，区间不重叠）—— 也就是说高分段「越难的题反而做得越快」在数据里是稳健的，只是被形状先验压成了平线，这是 2200–2400 三档共用 47.07 分钟的直接原因。

**拟合范围只定义一次**：`core.mjs` 的 `FIT_MIN_Q` / `FIT_MAX_Q`（当前 800–2400，2026-09-21 从 2100 抬上来；抬高会让**整条曲线**重算，低分段读数也会动，因为核平滑的带宽是在更宽的区间上选的）。`smooth-fit.mjs`、`monotone-fit.mjs`、`fit.mjs`、`table.mjs`、`compare.mjs` 全部从这里取，`plot.py` 因为 Python 不能 import `.mjs`，在文件顶部保留了一份同值镜像并注明。范围不一致的后果是最右端的边界效应对不上：核平滑在区间端点没有外侧数据可借，多一个档位或少一个档位会改变最后一档被拽动的方向和幅度。`analyze.mjs` 更宽（800–2500 全算），以便敏感性分析看到高段明细。**端点必须是 100 的倍数**：出表脚本按 100 步长在 CSV 里精确查表（`Number(x.q)===q`），端点不对齐会让最后一档静默失踪。`core.mjs` 的 `fitGrid()` 对此直接抛错，`tests/cf-study.test.ts` 里有一条用例守着。

**三个偏差要分开**（`CENSORING.md` 逐步说明）：① 条件在解出 → KM 能修；② **条件在「到达该题」** —— 一行样本存在的前提是前面所有题都解出了，慢选手走不到，**KM 修不了**，这是选择不是删失；③ 题位（Easy/Hard）的归属时间 → **已按下面这条改掉**。

**用时口径：题位内共用起点（2026-09-18 改）**：`core.mjs` 按 standings 顺序走，`time = 上一个题位的 AC → 本题的 AC`，遇到没解出的题就 `break`。所以题序位置本身是读数的一部分，跨题序不可直接比 —— 这也是 `PLATEAU_CAUSE.md` 表 4 存在的理由。

改动在这里：**同一个题位（题号去掉尾数字）里的子任务共用同一个起点**，每个子任务各出一条记录。于是 `C2` 的用时是「冷启动 → 解出 `C2`」的整段，而不是「解出 `C1` 之后的增量」—— 后者既漏掉了 `C1` 那一段，样本又必然只含「刚做完近乎同一道题」的人（`2219:B2` 的增量中位只有 **1.4 分钟**）。`C1` 自己的记录原样保留，所以 **Easy 版的低档样本一条不丢**（`samples.json` 621,521 行，比修复前的 618,907 还多）。

### 按比赛留出验证（`validate.mjs`）

核平滑和保序回归都是描述性平滑 —— 它们在**自己拟合过**的档位上当然贴合原数据，`MONOTONE.md` 里那句「平滑后仍落在经验点 95% 区间内」说的就是这件事，它证明不了这条曲线拿去预测新比赛准不准。`validate.mjs` 负责回答后者。

分组单位是**比赛**而不是样本行：同一场比赛里几千条「选手×题目」记录高度相关，按行分折会让训练集和测试集共享比赛，误差被系统性低估。69 场比赛随机分 5 折、重复 8 次（不同随机划分），共 40 个折实例；每个折实例用其余折**重新走一遍生产流程**（含重新选带宽），再在留出折上评分。评估点取 `table.mjs` 读表的同一批 100 步长档位，所以验的就是要上线的那条曲线。

四个候选预测器，全部在训练集上重新拟合：

| 预测器 | 含义 |
|---|---|
| `constant` | 训练档位的加权平均 —— 「难度与耗时无关」的零模型 |
| `raw` | 直接用训练档位的经验点，不平滑 |
| `smooth` | 生产带宽选择 + 核平滑，未约束 |
| `monotone` | 核平滑 + 保序回归，**当前主推** |

评分目标是留出折自己的经验点估计（成功者中位耗时，主口径 ±100、赛前 rated ≥10，与生产完全一致），要求该档在留出折里至少有 3 场独立比赛、100 条样本 —— 拿纯噪声目标去罚预测器没有意义。

**三条判据在跑之前就定好**（避免事后挑指标），`diagnostics.json` 的 `productionReady` 由它们共同决定，三条全过才置 `true`：

1. 主推的 RMSE 低于常数基线，且配对区间（按折实例聚类 bootstrap）不含 0；
2. 主推不比「训练档位经验点」差 10% 以上 —— 这是平滑与单调约束的代价上限；
3. 时间留出方向一致：用 2026 之前的比赛拟合，预测 2026 的比赛，主推仍然优于常数。

除判据外还输出三样诊断：**反转复现率**（每个相邻档位对在留出集里下降的比例，用来判断反转是不是噪声）、**逐档覆盖率**（留出折自己的 bootstrap 区间是否罩住预测值）、**带宽稳定性**（重新选带宽的分布）。

**关于「未约束对照」之外还得有一层检查**：`compare.mjs` 找的是「九种筛选口径下区间不重叠」的反转，那仍是样本内的。`validate.mjs` 的复现率是**样本外**的独立证据 —— 当前 3 处稳健反转（1200→1300、1400→1500、1800→1900）全部在没参与拟合的比赛上复现。另外它检查了一个必须排除的替代解释：归属时间是「上一个题位的 AC → 本题的 AC」，题序位置本身就是读数的一部分，而高档位系统性地由靠后的题构成（800 档平均题序 1.20，1400 档以上 0% 的样本题序 ≤2）。把样本限制到「题序 ≥ 3」重算后反转依然下降，所以反转不是题序造成的 —— 但「只用题目 Rating 一个维度」仍是这个估计量的结构性弱点。

**当前验证结论**：**三条全过，`productionReady = true`**（2026-09-18）。主推 5.28 分钟 vs 常数 8.86 分钟（配对区间 [+3.15, +4.02] 分钟）、vs 经验点 5.45 分钟（上限 6.00）、2026 时间留出 5.06 分钟 vs 常数 7.65 分钟。**判据 3 是修好题位口径之后才通过的**：修之前 2026 留出是主推 6.54 vs 常数 6.10（失败），因为留出集自己在高档位下降（1800→1900 −3.57、1900→2000 −2.15），而主推按构造不许下降；那个「下降」有很大一块正是 `X2` 增量口径造出来的假象 —— 见 `SLOT_CHECK.md` / `SUBTASK_MERGE.md`。修完之后留出集里只剩 2 处下降（1200–1300、1800–1900），方向仍与 `k` 折一致，但幅度已不足以翻转判据。

判据通过**不等于**曲线变成实测点：3 处稳健反转依然存在、被保序回归压平，所以逐档读数（尤其 1200–1300、1400–1500、1800–1900）仍要按「先验下的保守估计」来读。判据只保证整条曲线对留出目标的 RMSE 优于基线。

扩大版的目标是 800–2000 各档至少 100 条主口径记录。默认先选 40 场 2024–2025 比赛，再仅按官方题目难度补足每档至少 5 场的题目覆盖；实际样本覆盖仍需清洗后检查。另选 60 场 2022–2023 rated 比赛的 Rating 变更记录，与研究比赛的 Rating 变更一起组成可核验的历史记录。无有效 Rating 变更的比赛不作为历史证据。

新队列不再仅抽取 120 位选手，而是纳入所选比赛中所有能证实符合参赛次数门槛的正式参赛者。`priorRatedKind=certified_lower_bound` 表示 `priorRated` 是抓到的、Rating 更新时间早于目标题比赛开始的不同比赛数下界；它达到 10 就足以证明实际参赛至少 10 场，但小于 10 **不证明**选手是新号。原有 120 位选手仍用完整 `user.rating`，标为 `exact`。

这种证据门槛会偏向在所选历史比赛中更活跃的选手，仍不是全体同 Rating 用户的无偏样本。前后结果变化混有队列变化；本轮比较的 A/B 使用同一候选队列。每个样本都保留精确历史/下界证据标记，输出两种数量。

扩大版新增 gzip 原始缓存，兼容先前 JSON 缓存；`expanded-progress.json` 可查看抓取进度，`samples-expanded.json` 保存阶段样本。完成后更新主数据文件。首次扩大时，小实验复制到 `results/cf-study-first-batch/` 与 `data/cf-study/runs/first-batch/`；不会覆盖这份对照存档。

两种 T97 都提供 95% 比赛聚类 bootstrap CI，同一轮随机重采样同时计算 A=KM 中位数、B=成功者中位数和 A−B，从而提供配对差值区间。实现先排序再按比赛重复次数缩放权重，已用显式重复抽样校验等价性。输出 `comparison.csv`、`COMPARISON.md`、`plots/t97-comparison.png/svg`；`REPORT.md` 同步为最新对比报告。

拟合阶段对每档点估计使用有效样本量加权多项式，候选一次/二次/三次，按留一 Rating 档交叉验证选择。这只是平滑查表候选，不能外推到 `FIT_MIN_Q`–`FIT_MAX_Q` 之外，也不替换经验点估计。输出 `t97_fitted.csv`、`fit_metrics.csv` 和 `fit.json`。实际用于查表的主推值来自核平滑 + 保序回归版本（见上文「曲线形状」），主表是 `T97_TABLE.md`。

## 抽样与清洗

1. 2024–2025 年已结束的 Div.2、Div.3、Educational、Div.1+2 比赛；按固定 SHA256 顺序，在四类比赛间轮选。然后按 problemset 中的官方难度，贪心补足 800–2000 题目档位覆盖，平局仍按 SHA256。这可能增加实际比赛数；不保证每档筛选后都有样本。未按比赛结果挑选。确实有 ratingChanges 的比赛才纳入，不把名称当 rated 证明。
2. standings 整场获取，只传 `contestId`。2026-09-16 实测带 `showUnofficial` 会返回 HTTP 400，因此在本地筛选正式单人 CONTESTANT。
3. 获取整场 `contest.status`，只保留比赛时段内的正式提交。最终判决 OK 的首次提交作为 AC 时间，不用 standings 的 bestSubmissionTime 近似首次 AC。不处理 IOI 部分分制。
4. 严格按 standings 的题目顺序推进；所有前题依次 AC，以前一道 AC 为起点。目标题提前有提交、或期间任何更后题有提交，停止纳入后续序列。最终未 AC 的下一题在比赛结束右删失，包括没有向该题提交的选手，避免只保留尝试者/成功者。
5. 使用 `contest.ratingChanges.oldRating`，联结 `user.rating` 再检查当前场 oldRating 一致。只有 rating 更新时间早于本场开始的历史场次计入 priorRated；本场和未来场次不计入。
6. 候选范围 ±150，分析输出 ±50/±100/±150 × 历史场次 ≥5/≥10/≥20 全部九种组合。高斯权重固定 σ=75；主口径 ±100、≥10。
7. 为限制首次历史查询成本，按题目 Rating 桶轮询、按 handle 的 SHA256 顺序选取最多指定数量的唯一选手。一次查到的选手在所有已选比赛中的合格候选记录都会纳入。这是探索性覆盖抽样，**不是全体候选人的等概率抽样**，高参与度选手可能更易进入样本；尚未计算纳入概率或逆概率权重。不能据此宣称总体无偏。

## 统计输出与边界

- `t97_raw.csv`：18 个 Rating 档全部保留；无数据、KM 不到 0.5 分别明确标注。数量包含比赛数、题目数、唯一选手数、选手×题目样本数、成功/删失数、实际/加权解出率、有效样本量。
- `quantiles.csv`：成功者 P10/P20/P30/P50/P70/P80/P90/P95；同时提供加权与不加权结果，单位为秒。
- `sensitivity.csv`：九种筛选组合。样本 <30 或有效比赛 <5 标为 small_sample，此门槛只是提示，不是通过门槛就有效的统计保证。
- `survival_curves.json`：主口径完整加权 KM 阶梯及 t/T_solve50 标准化坐标，无法识别时不生成该标准化。
- `plots/`：matplotlib 绘制经验 KM 中位数和有限 95% bootstrap CI、成功者 P50/P90、标准化叠加曲线；不平滑，不强制单调。未识别的 bootstrap 中位数作为 +∞ 保留，不能丢掉后只对有限样本算 CI；CSV 空上界并配合 ciStatus=upper_unbounded 表示无有限上界。一场比赛不能提供跨比赛 cluster CI。
- bootstrap 以比赛为 cluster，固定随机种子。可保护同场问题/选手相关性，但同一选手跨比赛仍有依赖；少量比赛下 CI 很不稳定，不能作为精确总体区间。

**主要识别限制**：读题起点不可观测；顺序筛选依赖之后的行为，会选择性排除跳题/放弃者；比赛结束删失与前题耗时、能力可能相关，独立删失假设不保证成立。800 是题目 Rating 下界，存在难度压缩；赛时表现与练习时无压力计时也不同。题目 rating 是抓取时的官方值，不是历史赛时快照。不得把经验 KM 解释成因果难度标尺。

在少量比赛/选手下不报告“显著增长”或拟合优劣。`t97_fitted.csv`（多项式）、`t97_smooth.csv`（核平滑）与 `t97_monotone.csv`（核平滑 + 保序回归）都只是描述性平滑，不替换 `t97_raw.csv` 里的经验点估计。下一阶段应先扩大跨年份、跨题目的覆盖，修正抽样权重，再比较未标准化/标准化曲线、按比赛留出验证统一映射。候选 Achievement 函数必须保证以成功者中位数映射到 97；98/99/99.5/100/100.5 的分位点属于产品效用选择，数据本身不能唯一确定，现阶段保持未定。

数据定义参考 [Codeforces API 对象文档](https://codeforces.com/apiHelp/objects)、[官方题目难度介绍](https://codeforces.com/blog/entry/62865)。公开提交数据集只有在能恢复正式参赛身份、比赛边界、未解出者及赛前历史时才可替代当前来源；本次直接使用官方 API，不混入 Kaggle 或 Hugging Face 样本。
